Я бы строил это приложение не просто как «словарь + карточки», а как систему с **двумя независимыми слоями знания**:

1. **Знаю слово и его значение.**
2. **Умею правильно изменять это слово.**

Это хорошо ложится на твои `words.json` + `inflections.json`: пользователь может знать, что `absolwent = выпускник`, но при этом путаться между `absolwenta / absolwentowi / absolwentem`.

И небольшая терминологическая поправка: для всего списка лучше говорить **lemma / словарная форма**, а не «инфинитив». Инфинитив существует только у глаголов.

## 1. Главные разделы приложения

Я бы сделал 4 раздела:

| Раздел              | Что изучаем                                 |
| ------------------- | ------------------------------------------- |
| **Слова**           | значение и узнавание лемм любых частей речи |
| **Существительные** | падежи, число, род                          |
| **Глаголы**         | лица, числа, времена и формы                |
| **Прилагательные**  | род, число, падеж, степени сравнения        |

Название **«Слова»** здесь лучше, чем «Общий»: оно сразу понятно пользователю.

Можно добавить пятый раздел позже:

**Повторение** — единая очередь SRS из всех остальных разделов.

Но на первом этапе я бы не делал его отдельным экраном. Кнопка `Повторить 34` может находиться прямо на главной.

# 7. Как строить обучение одного слова

Не стоит случайно выдавать упражнения.

Для нового слова я бы использовал progression:

```text
1. PL → RU choice
        ↓
2. RU → PL choice
        ↓
3. PL → RU input
        ↓
4. RU → PL input
        ↓
5. SRS
```

Но не обязательно делать все четыре за одну сессию.

Например:

### Первая встреча

```text
PL → RU choice
PL → RU recall
```

### через несколько минут

```text
RU → PL choice
```

### завтра

```text
RU → PL input
```

Это намного эффективнее, чем пять раз подряд показать одну карточку.

# 15. Что значит «частично изученное слово»

Это один из самых важных моментов всей архитектуры.

Не делай:

```ts
word.learned = true;
```

Этого недостаточно.

У слова должно быть несколько knowledge dimensions.

Например для существительного:

```ts
{
  lemma: "kobieta",

  vocabulary: {
    plToRu: ...,
    ruToPl: ...
  },

  morphology: {
    singular: {
      nominative: ...,
      genitive: ...,
      dative: ...,
      accusative: ...,
      instrumental: ...,
      locative: ...,
      vocative: ...
    },
    plural: {
      ...
    }
  }
}
```

Каждый `...` — собственное состояние знания/SRS.

То есть пользователь может иметь:

```text
kobieta

Перевод                   ✓
Mianownik                  ✓
Dopełniacz                 ✓
Celownik                   ✓
Biernik                    ✓
Narzędnik                  72%
Miejscownik                44%
Wołacz                     новое

Liczba mnoga               37%
```

Вот это и есть **частично изученное слово**.

# 16. Однако не стоит создавать SRS-карточку на каждую форму сразу

Это важное архитектурное ограничение.

У тебя:

```text
8000 слов
```

Если среднее число форм будет даже 20:

```text
160 000 карточек
```

А у глаголов может быть значительно больше.

Поэтому я бы использовал **динамические learning units**.

Например:

```text
kobieta|noun|sg|genitive
```

создаётся только после того, как пользователь начал тренировать этот падеж.

То есть БД содержит прогресс **только для реально встречавшихся пользователю упражнений**.

# 17. SRS

Я бы не писал классический:

```text
если правильно → +1 день
если неправильно → сегодня
```

Лучше сразу строить вокруг нормального spaced repetition.

Хорошая модель:

**FSRS**

Концептуально у learning item есть:

```ts
{
  stability,
  difficulty,
  lastReview,
  nextReview,
  reviewCount,
  lapseCount
}
```

И система решает, когда показать его снова.

Это пригодится как для:

```text
mieć → иметь
```

так и для:

```text
kobieta → sg/gen → kobiety
```

# 18. Active recall важнее recognition

Я бы специально разделил сложность заданий.

### Level 1 — recognition

```text
mieć

○ иметь
○ видеть
○ знать
○ идти
```

### Level 2

```text
иметь

○ mieć
○ wiedzieć
○ widzieć
○ iść
```

### Level 3

```text
mieć → [иметь]
```

### Level 4

```text
иметь → [mieć]
```

И только после production-задач считать слово реально хорошо известным.

Потому что выбор из четырёх вариантов сильно переоценивает знание.

# 19. Distractors — неправильные ответы

У тебя есть уникальное преимущество — 8000 реальных слов.

Для multiple choice не надо выбирать случайные неправильные ответы.

Например:

```text
wiedzieć
```

плохие distractors:

```text
арбуз
синий
бежать
окно
```

Слишком очевидно.

Хорошие:

```text
wiedzieć — знать
znać — знать/быть знакомым
myśleć — думать
rozumieć — понимать
```

Алгоритм выбора distractors:

```text
same POS
+
similar CEFR
+
similar frequency
+
prefer semantic similarity
```

Позже можно вручную/AI добавить `confusableWords`.

# 20. Ошибки тоже надо использовать

Приложение должно запоминать не только:

```text
correct / incorrect
```

но и **что пользователь написал**.

Например:

```text
question:
kobieta / locative sg

expected:
kobiecie

answer:
kobiety
```

Потом можно обнаружить:

```text
Ты часто путаешь
Dopełniacz ↔ Miejscownik.
```

И автоматически создавать тренировку на слабое место.

Это может стать одной из самых сильных функций приложения.

# 27. Архитектура прогресса без авторизации

Раз авторизации пока нет, я бы хранил всё локально.

Не `localStorage`, потому что данных постепенно станет много.

Используй:

**IndexedDB**

Например через:

```text
Dexie
```

Статические:

```text
words.json
inflections.json
```

можно держать в bundle/static assets.

А IndexedDB содержит только пользовательские данные:

```ts
wordProgress
formProgress
reviews
settings
sessions
```

# 28. Пример модели прогресса

Я бы примерно так разделил:

```ts
type WordProgress = {
  key: string; // "mieć|VERB"

  status:
    | 'new'
    | 'learning'
    | 'known'
    | 'mastered';

  vocabulary: {
    plToRu?: LearningState;
    ruToPl?: LearningState;
  };
};
```

Отдельно:

```ts
type FormProgress = {
  wordKey: string;

  dimension: string;
  // например:
  // "noun:sg:genitive"
  // "verb:present:1:sg"
  // "adj:sg:f:genitive"

  state: LearningState;
};
```

И:

```ts
type LearningState = {
  difficulty: number;
  stability: number;

  lastReviewAt?: number;
  nextReviewAt?: number;

  correct: number;
  incorrect: number;
};
```

Таким образом `words.json` остаётся **immutable dataset**, а пользовательский прогресс вообще не загрязняет его.

Не пытался бы сразу реализовать все польские формы.

### Phase 3 — Verbs

```text

```

### Phase 4 — Adjectives

```text

```

### Phase 5 — Context

Самая интересная стадия:

```text

nowy / nowego / nowym
```

или

```text

```

То есть перейти от:

> «дай Genitive»

к настоящему языку:

> «выбери форму, которая нужна в этом предложении».

# 30. Я бы немного изменил твою концепцию «изучено полностью / частично»

На UI можно показывать:

```text
Новый
Изучаю
Знаю
Освоен
```

Но внутри состояния не должны быть бинарными.

Например:

```text
człowiek

Значение                    96%
Склонение                    64%

  Singular                   88%
  Plural                     42%

Общее владение               72%
```

Причём **72% не нужно хранить** — это вычисляемое значение из отдельных learning units.

# 31. Итоговая концепция

По сути приложение будет состоять из трёх слоёв:

```text
                  POLISH VOCABULARY
                         │
              ┌──────────┴──────────┐
              │                     │
          Vocabulary            Morphology
              │                     │
      ┌───────┴────────┐     ┌──────┼───────┐
      │                │     │      │       │
    PL→RU            RU→PL  Nouns  Verbs   Adj
      │                │     │      │       │
      └────────────────┴─────┴──────┴───────┘
                         │
                        SRS
                         │
                   User progress
```

Главный принцип, который я бы заложил сейчас:

> **Не слово является минимальной единицей обучения, а навык, связанный со словом.**

Например `kobieta` — это не одна карточка. Это набор навыков:

```text
kobieta → женщина
женщина → kobieta

kobieta → gen.sg → kobiety
kobieta → dat.sg → kobiecie
kobieta → inst.sg → kobietą
...

kobieta → gen.pl → kobiet
...
```

И приложение постепенно активирует эти навыки по мере обучения. Именно такая модель позволит позже добавить **падежи, времена, контекстные предложения, слабые места и адаптивную тренировку**, не переделывая всю архитектуру.
