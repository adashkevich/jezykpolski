# 33 — Ранжирование блоков тренировки по использованию с затуханием по времени

**Зависит от:** 05, 24, 32
**Результат:** приложение запоминает, какие блоки тренировки пользователь реально
запускает, и поднимает наверх самые востребованные — с учётом давности: сто запусков
месячной давности проигрывают десяти сегодняшним.

---

## Требования: FR-113, FR-141, FR-142

## Зачем

После задачи 32 экран тренировки — список свёрнутых блоков, и порядок в этом списке
становится главным элементом навигации: верхний блок открывается одним нажатием, нижний
требует скролла. Фиксированный порядок обслуживает среднего пользователя, которого не
существует: кто-то живёт в падежах существительных, кто-то каждый день гоняет написание
слов и никогда не открывает конфигуратор форм.

Простой счётчик запусков эту задачу не решает: он навсегда закрепляет сверху то, чем
человек пользовался в первую неделю. Нужен показатель, в котором старые запуски
обесцениваются — «сто раз месяц назад, десять раз сейчас» должно дать преимущество
новому блоку (формулировка требования дословно).

## 1. `learning/practice/block-usage.ts` — чистый модуль

Без React и Dexie (`learning/**` — чистый слой). Экспоненциальное затухание с периодом
полураспада:

```ts
/** Период полураспада веса запуска. 7 дней подобрано под требование FR-141: 100
 *  запусков 30-дневной давности весят 100 * 0.5^(30/7) ≈ 5.1 — меньше, чем 10 сегодняшних. */
export const USAGE_HALF_LIFE_MS = 7 * 24 * 60 * 60 * 1000

export interface BlockUsage {
  /** Накопленный вес, уже приведённый к моменту `updatedAt`. */
  readonly score: number
  readonly updatedAt: number
  /** Сырой счётчик запусков — не участвует в сортировке, нужен для отладки и для
   *  осмысленного экспорта/импорта. */
  readonly runs: number
}

export type BlockUsageMap = Readonly<Record<string, BlockUsage>>

/** Значение `score`, приведённое к моменту `at`. Чистая функция от записи. */
export function decayedScore(usage: BlockUsage | undefined, at: number): number

/** Новая карта с учтённым запуском блока `id` в момент `at`:
 *  `score = decayedScore(prev, at) + 1`, `runs += 1`, `updatedAt = at`. */
export function recordBlockRun(map: BlockUsageMap, id: string, at: number): BlockUsageMap

/** Порядок блоков: по убыванию `decayedScore(…, at)`; при равенстве (в том числе у всех
 *  неиспользованных, у которых счёт 0) — по порядку в `defaultOrder`, то есть сортировка
 *  устойчива и первый заход выглядит ровно как задача 32 его описала. */
export function orderBlocks(
  defaultOrder: readonly string[],
  map: BlockUsageMap,
  at: number,
): string[]
```

Свойства, которые обязаны быть покрыты тестами:

- запись со `score = 100`, `updatedAt` 30 дней назад даёт `decayedScore` меньше, чем запись
  со `score = 10` и `updatedAt = at` (буквальная проверка формулировки требования);
- `recordBlockRun` не переписывает счёт других блоков;
- `orderBlocks` на пустой карте возвращает `defaultOrder` без изменений;
- порядок устойчив: блоки с одинаковым счётом не меняются местами между вызовами;
- неизвестные `id` в карте (например, блок, удалённый более новой версией приложения)
  игнорируются `orderBlocks` и не ломают порядок.

Хранение приведённого счёта вместо журнала запусков — сознательное решение: карта из
пяти чисел, никакой миграции схемы, и стоимость не растёт с историей. Точность при этом
не теряется — экспоненциальное затухание ассоциативно, поэтому «затухнуть и прибавить»
даёт тот же результат, что «просуммировать затухшие веса всех запусков».

## 2. Персистентность

Ключ `practiceBlockUsage` в существующей таблице `settings` через
`db/repositories/settings.repository.ts` (`get`/`set`) — новой Dexie-таблицы и, значит,
`version(2)`-миграции эта задача **не требует**. Значение — `BlockUsageMap`.

Экспорт/импорт (задача 24) забирает `settings` целиком, поэтому ключ переносится между
устройствами сам собой; отдельной ветки в бэкапе не добавляется. Сброс данных обнуляет
порядок вместе со всеми настройками — это ожидаемо.

Тонкость записи: карта читается и пишется в одном месте (§3), запись асинхронная и не
блокирует навигацию — «Начать» не должен ждать IndexedDB, чтобы стартовать сессию.

## 3. `features/training-setup/hooks/useTrainingBlockOrder.ts`

Хук, который экран тренировки использует вместо статического массива блоков:

```ts
export function useTrainingBlockOrder(defaultOrder: readonly string[]): {
  readonly order: readonly string[]
  readonly recordRun: (id: string) => void
}
```

1. На монтировании читает `practiceBlockUsage` и один раз вычисляет `orderBlocks(...,
   Date.now())`. Порядок фиксируется на время жизни экрана — блоки не должны
   переупорядочиваться под пальцем после нажатия «Начать».
2. До завершения чтения возвращает `defaultOrder` — экран рендерится сразу, без скелетона
   и без прыжка порядка на 320px (перерисовка происходит один раз, до первого
   взаимодействия).
3. `recordRun(id)` вызывается в обработчике «Начать» каждого блока, включая
   «Тренировку форм слов» — это тот же `id`, что `TrainingBlockProps.id` из задачи 32.
   Запись идёт `void`-ом, ошибки записи логируются и не мешают старту сессии.

`TrainingSetupScreen` рендерит блоки в порядке `order`, «Выборка слов» в ранжировании не
участвует и всегда остаётся первой (задача 32 §1).

## 4. Что не ранжируется

- Разделы NOUN/VERB/ADJ (табы «Выборки слов») — это фильтр, а не точка входа; их порядок
  фиксирован, последний выбранный и так восстанавливается из `lastPracticeConfig`.
- Главный экран и нижняя навигация — вне этой задачи.
- Никакой телеметрии наружу: карта не покидает IndexedDB устройства (NFR — приложение без
  бэкенда).
