# 11 — FSRS-адаптер и политика SRS

**Зависит от:** 03, 05
**Результат:** планирование повторений через `ts-fsrs`, изолированное за адаптером, с правилами демпфирования.

---

## Шаги

### 1. Адаптер

`src/learning/srs/fsrs-adapter.ts` — **единственное место в проекте**, где импортируется `ts-fsrs`
(blueprint §13, §36.11). ESLint-правило `no-restricted-imports` запрещает импорт `ts-fsrs` где-либо ещё.

```ts
createInitialState(now: number): SrsState
review(state: SrsState, rating: Rating, now: number): { next: SrsState; log: SrsLogEntry }
previewIntervals(state: SrsState, now: number): Record<Rating, number>
isDue(state: SrsState, now: number): boolean
```

`SrsState` — собственный тип приложения (поля `state / stability / difficulty / due / reps /
lapses / lastReviewAt`), адаптер конвертирует его в `Card` библиотеки и обратно.
Наружу типы `ts-fsrs` не протекают.

Все временные метки — `number` (epoch ms), не `Date`: индексируется в Dexie и корректно
сериализуется в экспорт.

### 2. Маппинг результата упражнения в рейтинг

```text
неверный ответ                            → Again
верный, но nearMiss (ошибка в диакритике) → Hard
верный, выбор из вариантов                → Good
верный, ввод текста                       → Easy
самооценка                                 → рейтинг выбирает пользователь напрямую
```

### 3. `learning/srs/policy.ts` — демпфирование

Два правила, без которых SRS даёт ложную уверенность (app-design §22, §24):

**Правило 1 — повтор ошибки внутри сессии (FR-103).**
Пользователь ошибся, увидел правильный ответ, через 20 секунд повторил его.
Считать это успешным повторением нельзя.

```text
SRS-состояние навыка обновляется только по ПЕРВОМУ ответу на этот навык в рамках сессии.
Последующие попытки пишутся в reviewLogs с srsApplied: false.
```

Реализуется через `firstAnswerBySkill` в стейте сессии (задача 13).

**Правило 2 — режим Practice (FR-112).**
Пользователь сам выбрал, что тренировать. Это не то же самое, что выданное планировщиком повторение.

```text
при mode === 'practice':
  рейтинг не может быть выше Good
  вычисленный интервал умножается на PRACTICE_INTERVAL_FACTOR (0.5)
```

Обе константы — именованные, в одном месте, покрыты тестами.

### 4. Ленивая материализация при планировании

`getDueSkills` возвращает только **существующие** записи. Новые навыки приходят не оттуда,
а из отдельного источника: «сколько новых слов взять сегодня» (настройка, FR-133).
Сборка очереди — задача 13.

### 5. Счётчики для главной и статистики

```ts
countDue(now)                      // «Повторить N»
countDueBetween(startOfTomorrow, endOfTomorrow)   // «завтра»
countDueBetween(now, now + 7d)     // «7 дней»
```

Границы суток считаются в локальной таймзоне пользователя. Не UTC — иначе «сегодня» будет
съезжать. Хелперы в `lib/dates.ts`, нативный `Date`, без date-библиотек (blueprint §31).

## Acceptance

- [ ] `ts-fsrs` импортируется ровно в одном файле; ESLint запрещает остальные импорты
- [ ] Типы `ts-fsrs` не встречаются в сигнатурах вне адаптера
- [ ] `review` с рейтингом `Again` возвращает `due` в пределах текущего дня
- [ ] `review` с рейтингом `Easy` даёт больший интервал, чем `Good`, при том же состоянии
- [ ] Round-trip `SrsState → Card → SrsState` не теряет данных
- [ ] Правило 1: второй ответ на тот же навык в сессии не меняет `SkillRecord`, но пишет лог с `srsApplied: false`
- [ ] Правило 2: интервал в practice-режиме строго меньше, чем в learn при том же рейтинге
- [ ] Правило 2: рейтинг `Easy` в practice трактуется как `Good`
- [ ] `countDue` для пустой БД = 0, не падает
- [ ] Границы «сегодня/завтра» корректны при смене таймзоны в тесте
