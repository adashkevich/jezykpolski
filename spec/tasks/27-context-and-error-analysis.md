# 27 — Контекстные предложения и анализ ошибок

**Зависит от:** 21, 22, 23
**Статус:** вне MVP. Фаза 5 по app-design §29.

---

## Требования: FR-63, FR-104, FR-105, FR-94, FR-56, FR-57

## Зачем

Это переход от «дай Genitive» к настоящему языку: «выбери форму, которая нужна в этом
предложении». Пользователь перестаёт учить название падежа и начинает учить, **когда** он нужен.

Одновременно — самая сильная потенциальная функция приложения (app-design §20):
использование собственных ошибок пользователя.

---

## 1. Анализ ошибок (FR-104, FR-105)

Данные для этого **уже собираются с MVP**: `reviewLogs.answerGiven` + `skillId`
(задача 05, `architecture.md` §8). Никаких изменений схемы не потребуется.

### Матрица путаницы

Для каждой ошибки известно: ожидаемый слот и введённая форма. Если введённая форма
принадлежит **другому слоту той же парадигмы** — это не случайная ошибка, а системная путаница:

```text
question: kobieta / locative sg
expected: kobiecie
answer:   kobiety            ← это genitive sg того же слова
```

Накопив такие пары, показать:

```text
Ты часто путаешь
Dopełniacz ↔ Miejscownik.

[ Потренировать ]
```

### Автотренировка слабого места (FR-105)

Кнопка собирает practice-очередь из двух путаемых измерений на словах, где уже были ошибки.
Использует существующий `buildPracticeQueue` (задача 19) — новой инфраструктуры не нужно.

## 2. Контекстные предложения (FR-63)

```text
Nie ma ______.
  kobieta / kobiety / kobietą / kobiecie
```

```text
Mam ____ samochód.
  nowy / nowego / nowym
```

### Источник предложений — открытый вопрос

Требует решения до реализации:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Шаблоны по падежам («Nie ma ___» → genitive) | Полностью офлайн, детерминированно, дёшево | Однообразно, не все слова подходят семантически |
| Корпусные примеры | Естественный язык | Нужен новый источник данных, лицензия, объём |
| Генерация LLM на этапе сборки | Качественно и разнообразно | Blueprint §1 запрещает LLM **в рантайме**; на этапе сборки — допустимо, но требует ревью качества |

Рекомендация: начать с шаблонов по падежам для 200–300 самых частотных существительных.
Это даёт проверяемое качество без новых зависимостей. LLM-генерация на этапе сборки —
возможное расширение, но результат должен попасть в репозиторий как проверенные данные,
а не генерироваться на лету (это нарушило бы офлайн-требование).

## 3. `confusableWords` (FR-94)

Ручной или сгенерированный на этапе сборки список семантически близких слов
(`wiedzieć / znać`, `myśleć / rozumieć`) — улучшает дистракторы сверх эвристики
«та же POS + близкая частота» (задача 10).

Хранится как отдельный артефакт контента, подключается в `pickVocabDistractors`
без изменения его сигнатуры.

## 4. Прочие упражнения этой фазы

- Matching (FR-55) — соединить 4–5 пар PL↔RU
- Найди лишний перевод (FR-56)
- Быстрая классификация части речи (FR-57)

Все три — новые типы в существующем discriminated union, добавляются без правки runner'а
(задача 09, п.1). Это и есть проверка того, что архитектура движка выбрана верно.
